# Taste
- Prefers database changes delivered as a standalone SQL script (e.g. `sql/*.sql`) that can be run manually on MySQL, rather than only via migrations/auto-sync; repeatedly asks for the ALTER/UPDATE SQL to be handed over alongside the code change ("also gimme sql to update table column"). Confidence: 0.7
- Expects a new field/attribute to be plumbed end-to-end through every layer that stores, ingests or exposes it — the ORM model (docblock, validation rules, labels), the controller (entity fields, serializer, sync/ingest), the schema DDL, and any docs — rather than only the layer named in the request; states this explicitly ("pls update model also") and chains the layers in one request ("pls update the code for populate data and sync, then continue update gmrcontroller"). Confidence: 0.7
- Expects a simple, copy-paste-ready curl example for new/changed HTTP endpoints, and prefers terse response payloads limited to the identifiers that matter (e.g. invoice id + status). Confidence: 0.6
- Wants sync/import logic to be idempotent: a re-sync must update the existing record in place, keyed by the record's natural identity, and must never create duplicate rows (e.g. duplicate invoices). Confidence: 0.7
- Treats "no duplicates" as covering child/detail rows as well as the parent record, and expects existing rows in the database to be audited/cleaned up — not just freshly written data. Confidence: 0.6
- Expects HTTP endpoints to be documented end-to-end: a markdown reference plus an OpenAPI/Swagger-style interactive UI, covering every endpoint with curl examples. Confidence: 0.6
- When documentation exists for one controller, expects it extended to the whole API surface ("pls also create for other controllers") — favors broad coverage over just the piece named. Confidence: 0.5
- Expects list/collection endpoints to support pagination, and prefers it implemented using the project's established convention (e.g. Yii `Pagination` + `X-Pagination-*` headers) rather than a bespoke scheme. Confidence: 0.5
- Expects list/collection endpoints to support sorting and richer filtering (e.g. sort field + direction, multi-value filters), implemented following the project's existing param conventions rather than a one-off scheme. Confidence: 0.5
- Writes instructions as short, terse, unpunctuated notes (e.g. "look gmrcontroller, at sync, invoices must not duplicated, just update the old data"; "pls add endpoint to get invoice data (with details)") — prefers concise replies over lengthy explanation. Confidence: 0.6
- When syncing/importing data, expects rows carrying no meaningful value to be discarded rather than persisted (e.g. skip rows whose amount is 0 or negative) — values data hygiene at ingest time, not just correctness of the records that are saved. Confidence: 0.5
- Wants each imported record to carry its origin/provenance — e.g. the originating sheet name saved on the row via `source_sheet`, with a row-level value taking precedence over the payload-level one. Actively verifies this in the database and flags it as a bug when a hardcoded fallback (e.g. `'API'`) overrides the supplied origin. Confidence: 0.7
- When adding to an existing doc/file, expects the new content to match that file's established language and formatting conventions (e.g. extends an Indonesian-language API doc in Indonesian, reusing its section numbering/subsections) rather than imposing a fresh style. Confidence: 0.5
- Expects documented request/response examples to be faithful to what the code actually emits (real field names/order), verified by running the real serializer/encoder rather than hand-written approximations. Confidence: 0.5
- Bilingual Indonesian/English: writes requests in either language (e.g. "tolong migrasikan project yii2 ini ke php 8.4" alongside English one-liners) and is comfortable with replies in Indonesian that keep technical terms/filenames in English — match the language of the user's message. Confidence: 0.5
- Communicates an authoritative data layout by pasting the literal source (e.g. the spreadsheet's tab-separated header row: `Date	ID	INVOICE NUMBER	BILLED TO	...	Fee (%)	Fee (Rp)	Total`) or by citing the exact columns by letter ("sync status and sync_date is on column O and P"), and expects the code's column/index mappings to match that layout position-for-position, including columns the code does not yet consume. Confidence: 0.6
- Expects changes applied symmetrically across analogous record variants: whatever a direction (e.g. BUY invoices) already handles must also be handled for the parallel direction (SELL invoices) — the agent is expected to remember this without being told twice ("dont forget on invoice sell also have fee and total"). Confidence: 0.55
- Treats the file as the user's to edit between sessions — they update it themselves and simply say "pls fix <file>" again when a previous change has been lost, expecting the agent to re-read the current file, spot the regression, and re-apply it rather than trust earlier state. Confidence: 0.5
- Models rate-driven monetary values as a percentage + value pair rather than a single amount — e.g. "add percentage and value" splits one `tax` field into `tax_pct` (rate) and `tax_amount` (computed IDR value); again for a line `fee` ("it has fee, in percentage and value") into `fee_pct` / `fee_amount`, and again for the header fee on the main invoice ("on main invoice, there is also fee(percentage and amount), pls add")) following the project's existing `<name>_pct` / `<name>_amount` naming convention. Expects the pattern applied consistently at every level, not just the record it was first introduced on. Confidence: 0.8
- Prefers values the source system already computes to be stored verbatim and never recomputed server-side: when a spreadsheet column/formula is authoritative, take the number from the cell rather than reimplementing the calculation in code ("di script, total ambil dari cell spreadsheet, jangan di hitung manual, karena rumusnya di spreadsheet sudah benar"). An empty source cell is stored as 0, not replaced by a derived fallback. Confidence: 0.75
