# Taste
- Prefers database changes delivered as a standalone SQL script (e.g. `sql/*.sql`) that can be run manually on MySQL, rather than only via migrations/auto-sync; repeatedly asks for the ALTER/UPDATE SQL to be handed over alongside the code change ("also gimme sql to update table column"). Confidence: 0.7
- Expects a new field/attribute to be plumbed end-to-end through every layer that stores, ingests or exposes it — the ORM model (docblock, validation rules, labels), the controller (entity fields, serializer, sync/ingest), the schema DDL, and any docs — rather than only the layer named in the request; states this explicitly ("pls update model also") and chains the layers in one request ("pls update the code for populate data and sync, then continue update gmrcontroller"). Confidence: 0.7
- Expects a simple, copy-paste-ready curl example for new/changed HTTP endpoints, and prefers terse response payloads limited to the identifiers that matter (e.g. invoice id + status). Confidence: 0.6
- Wants sync/import logic to be idempotent: a re-sync must update the existing record in place, keyed by the record's natural identity, and must never create duplicate rows (e.g. duplicate invoices). Confidence: 0.7
- Treats "no duplicates" as covering child/detail rows as well as the parent record, and expects existing rows in the database to be audited/cleaned up — not just freshly written data. Confidence: 0.6
- Expects HTTP endpoints to be documented end-to-end: a markdown reference plus an OpenAPI/Swagger-style interactive UI, covering every endpoint with curl examples. Confidence: 0.6
- When documentation exists for one controller, expects it extended to the whole API surface ("pls also create for other controllers") — favors broad coverage over just the piece named. Confidence: 0.5
- Expects list/collection endpoints to support pagination, and prefers it implemented using the project's established convention (e.g. Yii `Pagination` + `X-Pagination-*` headers) rather than a bespoke scheme. Confidence: 0.5
- Expects list/collection endpoints to support sorting and richer filtering (e.g. sort field + direction, multi-value filters), implemented following the project's existing param conventions rather than a one-off scheme. Confidence: 0.5
- Writes instructions as short, terse, unpunctuated notes (e.g. "look gmrcontroller, at sync, invoices must not duplicated, just update the old data"; "pls add endpoint to get invoice data (with details)") — prefers concise replies over lengthy explanation. Confidence: 0.6
- When syncing/importing data, expects rows carrying no meaningful value to be discarded rather than persisted (e.g. skip rows whose amount is 0 or negative) — values data hygiene at ingest time, not just correctness of the records that are saved. Confidence: 0.5
- Wants each imported record to carry its origin/provenance — e.g. the originating sheet name saved on the row via `source_sheet`, with a row-level value taking precedence over the payload-level one. Actively verifies this in the database and flags it as a bug when a hardcoded fallback (e.g. `'API'`) overrides the supplied origin. Confidence: 0.7
- When adding to an existing doc/file, expects the new content to match that file's established language and formatting conventions (e.g. extends an Indonesian-language API doc in Indonesian, reusing its section numbering/subsections) rather than imposing a fresh style. Confidence: 0.5
- Expects documented request/response examples to be faithful to what the code actually emits (real field names/order), verified by running the real serializer/encoder rather than hand-written approximations. Confidence: 0.5
- Bilingual Indonesian/English: writes requests in either language (e.g. "tolong migrasikan project yii2 ini ke php 8.4" alongside English one-liners) and is comfortable with replies in Indonesian that keep technical terms/filenames in English — match the language of the user's message. Confidence: 0.5
- Communicates an authoritative data layout by pasting the literal source (e.g. the spreadsheet's tab-separated header row: `Date	ID	INVOICE NUMBER	BILLED TO	...	Fee (%)	Fee (Rp)	Total`, and again `QTY PRICE AMOUNT Fee (%) Fee (Rp) Total d kolom K-P`) or by citing the exact columns by letter ("sync status and sync_date is on column O and P"), and expects the code's column/index mappings to match that layout position-for-position, including columns the code does not yet consume. The column *names* define their meaning (PRICE = the rate, AMOUNT = qty × rate) — a mapping inferred from a numeric coincidence in a previously generated payload is treated as a bug, so the latest copy of the user's own workbook is the final authority. Confidence: 0.7
- Expects changes applied symmetrically across analogous record variants: whatever a direction (e.g. BUY invoices) already handles must also be handled for the parallel direction (SELL invoices) — the agent is expected to remember this without being told twice ("dont forget on invoice sell also have fee and total"). Confidence: 0.55
- Treats the file as the user's to edit between sessions — they update it themselves and simply say "pls fix <file>" again when a previous change has been lost, expecting the agent to re-read the current file, spot the regression, and re-apply it rather than trust earlier state. Confidence: 0.5
- Models rate-driven monetary values as a percentage + value pair rather than a single amount — e.g. "add percentage and value" splits one `tax` field into `tax_pct` (rate) and `tax_amount` (computed IDR value); again for a line `fee` ("it has fee, in percentage and value") into `fee_pct` / `fee_amount`, and again for the header fee on the main invoice ("on main invoice, there is also fee(percentage and amount), pls add")) following the project's existing `<name>_pct` / `<name>_amount` naming convention. Expects the pattern applied consistently at every level, not just the record it was first introduced on. Confidence: 0.8
- Prefers temporarily disabling a feature by commenting the code out — leaving the original line commented (with the replacement alongside) so reverting is a one-line uncomment — rather than deleting it, and scopes the change to code only unless docs are explicitly named ("just comment the code"). Confidence: 0.6
- Reports bugs tersely and expects the agent to trace the root cause from the artifact given rather than asking clarifying questions — either pasting the raw failure output (HTTP status + JSON error payload, batch counters, console logs) or stating a concrete expected-vs-actual value with its authoritative source and the files to inspect ("qty is 45301.43, but on DB it changes to 45379, the correct one is 45301.43 (its from buy invoice data)"; "check gmrcontroller and invoices.json"). Confidence: 0.6
- Prefers values the source system already computes to be stored verbatim and never recomputed server-side: when a spreadsheet column/formula is authoritative, take the number from the cell rather than reimplementing the calculation in code ("di script, total ambil dari cell spreadsheet, jangan di hitung manual, karena rumusnya di spreadsheet sudah benar"). An empty source cell is stored as 0, not replaced by a derived fallback. Applies to derived-looking fields too (e.g. invoice `qty` must come purely from the INV_BUY sheet column, not from summing the detail rows). Confidence: 0.8
- Checks data provenance by asking where a value actually comes from (e.g. "untuk invoice buy, qty ambil dr mana?") and expects the agent to trace it end-to-end across the whole pipeline — spreadsheet → Apps Script payload → controller → DB — then fix every layer that gets it wrong (both the producer script and the controller that overwrites it), rather than patching only the layer named in the request. Confidence: 0.5
- Expects new sync capabilities/modes to be surfaced as their own entries in the spreadsheet's custom menu (the Apps Script menu UI) so they can be run by hand, not just as internal code paths — reminds the agent explicitly ("jangan lupa tambah menu baru ya"). Confidence: 0.55
- Wants sync to be incremental rather than a full re-send: a separate action that detects which rows are new/modified and sends only those, with changes detected automatically (no manual flagging) and stored state driving the comparison ("only proceed new data or modified data, so code detect if there is any changes and only newly / modified data will be sent"). Changing a detail/dependent row should count as a change to its parent record. Confidence: 0.6
- Works on a local Windows + Laragon stack: project `itrust` (legacy Yii2 PHP API) lives at `E:\laragon6\www\itrust` with MySQL locally (root, no password; DB e.g. `itrust_040826`). Laragon-managed Apache/PHP versions matter when debugging version-migration bugs — Apache's loaded PHP version is in `E:\laragon6\etc\apache2\mod_php.conf`, runtime errors go to `runtime/logs/app.log`, and vendor platform checks (`vendor/composer/platform_check.php`) can make endpoints 500 even when the app code is fine (e.g. vendor built for PHP >= 8.4 while Apache still loads 7.4.30). Confidence: 0.6
- Deploys the app to no-shell shared hosting (cPanel) rather than a shell-accessible server, so production issues must be investigable through uploadable single-file PHP probes, cPanel Metrics/Error logs, `~/.user.ini` + MultiPHP INI settings, and the app's `runtime/logs/app.log` — and expects the agent to supply that kind of step-by-step, file-access-only debugging playbook when something like a request timeout ("Timeout was reached … i uploaded on shared hosting, how to debug") happens in production. Confidence: 0.5
- Frontend is Astro.js calling the Yii2 backend through a proxy route kept as `example/proxy.js.example` (served at `/api/proxy`) that dispatches on an `action` name via an `endpoints` map to controller routes. Expects the proxy's action map to stay in sync with the backend as endpoints move (e.g. accounts actions leaving `MobileController` for `Mt4AccountController`), so existing frontend calls keep working — fix the mapping layer rather than silently changing callers. The same backend is consumed by more than one client — besides the Astro frontend there is a MetaTrader 5 EA (MQL5, `mt5/ITv2.mq5`) that authenticates through this proxy, so a failure can surface as the proxy wrapping a raw upstream response (e.g. an Apache HTML 500 arriving as `{ "raw": "<html>…" }`) rather than a clean Yii JSON body. Confidence: 0.55
- Keeps runnable API references in the repo (`example/curl_example_*.txt`, `example/proxy.js.example`) and treats them as living documentation: reports them as broken ("does not work anymore") and expects them to work again / be updated when endpoints, auth, or param placement change, instead of adding a new example file. Confidence: 0.5
- Insists on proving the root cause with concrete evidence before any code is changed: "Diagnose the true failure before changing anything", reassemble the exact HTTP status + raw response body + the matching error-log line, and expects the real failure to be demonstrated rather than guessed ("assume the bug is in the backend and prove it"). Names the decisive reproduction step himself (the direct `curl`) as the first command to run. Confidence: 0.65
- Prefers fixing a language/runtime migration by upgrading libraries to versions that support the new runtime over patching source to paper over incompatibilities (e.g. "upgrade yiisoft/yii2 instead of hand-patching signatures with `?Type` hacks", "Prefer upgrading libraries to PHP-8.4-compatible versions over patching code"). Confidence: 0.6
- Treats a shared API endpoint's response contract as frozen: when other clients (e.g. a native mobile app) consume it, the success payload shape must not change — add fields like error codes rather than altering the existing structure. Confidence: 0.6
- Wants distinct failure modes kept distinguishable instead of being collapsed into one generic catch: a post-auth/token/session error must surface as its own code+message, must not be reported as "Invalid username or password" or a generic "Login failed", and the underlying exception should be logged alongside the request. Values fail-fast misconfiguration errors (e.g. missing required params) over silent fallbacks. Confidence: 0.6
- Security-conscious about hardcoded/insecure defaults: expects hardcoded secret fallbacks removed in favour of requiring the real value from params/env, and rejects `Access-Control-Allow-Origin: '*'` combined with `Access-Control-Allow-Credentials: true` in favour of an explicit origin allow-list. Confidence: 0.6
- Prefers small, surgical changes scoped to the reported defect ("small, surgical"; "Do not fix this on the frontend; the frontend is not the problem") rather than broad rewrites or changes to parts explicitly declared out of scope. Confidence: 0.5
- CORS allow-lists must cover the real deployed frontend origin(s), not just the backend's own domain: the Astro frontend is hosted separately — a Cloudflare Pages deployment (e.g. `https://gmrinternationalid.pages.dev`) — so an allow-list containing only `itrust-tech.id` leaves the frontend blocked, which the user reports from the browser console as `No 'Access-Control-Allow-Origin' header is present on the requested resource` + `net::ERR_FAILED`. Expects the API to be callable from wherever the frontend actually runs. Confidence: 0.5
